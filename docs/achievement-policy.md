# Достижения ФСП: безопасный DEMO-компонент

В v0.5 ФСП был только фильтром. v0.6 добавляет отдельные вымышленные записи `fspAchievements` с `id`, `title`, `provenance=synthetic_seed`, `verified`, `specialization`, `grade`, `resultType` и `points`. `verified` здесь означает проверку внутри контролируемого синтетического fixture, не подтверждение из реестра. Все публичные записи принудительно получают префикс DEMO.

Запись учитывается только если профиль привязан, категория подтверждена, совпадают специализация и грейд записи, происхождение известно, `verified=true`, число points конечно и положительно. Одна привязка не даёт баллов. Пользовательская форма профиля не принимает достижения; демонстрационный адаптер создаёт заведомо вымышленную запись явным действием. Старые привязки без записей не мигрируют в выдуманные достижения.

Условия бонуса:

- В требованиях указаны точные специализация и грейд, совпадающие с кандидатом.
- Совпали все распознанные требования, включая стек и нижнюю границу опыта. Неизвестные/сложные требования требуют ручной проверки, ограниченность словаря явно показана.
- Берётся сильнейшая допустимая запись, не сумма. Значения ограничены: победитель ≤100, финалист ≤60, участник ≤20.
- Прибавка: `min(5 × max(points)/100, 100 − базовый балл)`; итог округляется до целого и не превышает 100. База остаётся 80% соответствия + 20% теста, без требований — только тест и без бонуса.
- Грейд, результаты теста и навыки не изменяются. Недостающий навык, другая категория и отсутствие подтверждения не компенсируются.

В карточке показаны источник, категория, тип результата и фактическая прибавка. Фильтр ФСП выбирает только профили с допустимой записью текущей категории. При отключении DEMO-связи достижения удаляются; повторное подключение создаёт текущий синтетический пример. Это средство демонстрации, не production-антифрод.

Будущий адаптер: FSP ID/Keycloak → согласие на чтение → backend проверяет подпись/источник и владельца subject → получает достижения из разрешённого API → нормализует категорию и статус → журналирует происхождение/время/отзыв → выдаёт только публичные безопасные поля. API, scopes, схема реестра и тестовый стенд должны быть подтверждены организаторами. Текущий код намеренно не принимает неизвестный `provenance` как реальное подтверждение.
