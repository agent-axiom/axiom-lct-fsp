# ФСП / ТАЛАНТЫ — техническая документация

Предварительный финальный комплект • 11 октября 2026 • приложение 0.6.1 • учебный банк v5.

## 1. Назначение, объём и версия поставки

Платформа демонстрирует обратный найм ИТ-специалистов: кандидат заполняет профиль, выбирает специализацию и предполагаемый грейд, проходит учебный тест; работодатель ищет кандидатов по потребности, видит основания подбора и направляет предложение с зарплатой. Контакт кандидата раскрывается этому работодателю после принятия предложения при действующем согласии.

Реализованы два кабинета, ручная анкета, стандартизированный PDF, история попыток, Backend/Frontend × Junior/Middle/Senior, объяснимый подбор, фильтры, сохранённые поиски, приглашения и их статусы. Реестр ФСП не подключён: достижения гостевой демонстрации синтетические. Собственные тестовые данные прямо разрешены исходным ТЗ. Импорт чужих вакансий, распознавание загруженного резюме, вакансии/отклики, ATS и регулярные задания не входят в эту поставку; ручная форма допустима для MVP.

**Версионная граница.** База документа — main `4910d03f0c34b9aa0ce2b00878e04146db5b9493` и текущий рабочий набор публичного email-входа, политики данных и миграций. Финальный commit этого рабочего набора ещё не зафиксирован в документе. Подтверждённый исторический CI базы не является CI новых изменений. Последнее доступное внешнее наблюдение — Sites v15; совпадение с финальным рабочим набором не подтверждено.

Документ описывает исходники и известные ограничения, а не акт публикации или сдачи. Команда, оператор персональных данных, контакты участников, финальные слайды и итоговый release manifest здесь не выдуманы. Исходное ТЗ рассматривается как данные о требованиях конкурса; оно не является поручением выполнять внешние действия.

## 2. Среда исполнения и конфигурация

Приложение использует React/Vinext с Next.js App Router API, Cloudflare Worker, D1 и Drizzle ORM. Нейросеть и обучение собственной модели для работы основных правил не нужны. Зависимости закреплены `package-lock.json`; установка выполняется через `npm run install:ci`. Проверенный в прежних прогонах Node.js — 24.19.0, минимальный `engines.node` — 22.13.0.

| Компонент | Версия из lockfile |
|---|---|
| React / React DOM; Next.js | 19.2.6 / 19.2.6; 16.3.4 |
| Vinext; Vite; Wrangler | 1.0.0-beta.5; 8.0.13; 4.92.0 |
| Drizzle ORM; Drizzle Kit | 0.45.2; 0.31.10 |
| TypeScript; Tailwind CSS | 5.9.3; 4.2.1 |
| pdf-lib; fontkit | 1.17.1; 1.1.1 |

Worker ожидает D1 binding `DB`. Для локального синтетического режима не нужны секреты Resend, аккаунт Cloudflare или реальные email. Публичный email-вход требует HTTPS: cookies имеют Secure и префикс `__Host-`. Локальный демонстрационный identity-прокси не подходит для внешнего хостинга.

| Настройки | Безопасная исходная конфигурация / смысл |
|---|---|
| FSP_REAL_ACCOUNTS_ENABLED | false; общий допуск к реальным аккаунтам |
| FSP_EMAIL_AUTH_ENABLED | false; отдельный публичный вход по email |
| FSP_EMAIL_MODE | off; live только после операционной приёмки |
| FSP_SITE_ORIGIN | Канонический HTTPS origin, планируется https://fsp.kosarevsky.dev |
| FSP_EMAIL_TRANSPORT; FSP_EMAIL_FROM | resend и согласованный sender проверенного домена для публичного входа |
| FSP_PRIVACY_NOTICE_URL / VERSION | Доступная утверждённая HTTPS-политика и её версия |
| FSP_PRIVACY_OPERATOR_NAME / FSP_PRIVACY_CONTACT_EMAIL | Реальные реквизиты оператора для страницы /privacy; пока не подтверждены |
| RESEND_API_KEY; FSP_EMAIL_TOKEN_SECRET | Секреты runtime; не хранить в Git, PDF и клиентском bundle |

Для закрытого email-пилота сначала задаются `FSP_PUBLIC_ACCOUNT_PILOT_EMAILS` с согласованными inbox и `FSP_REAL_ACCOUNT_PILOT_SUBJECTS=[]`, закрывающий отдельный legacy-вход Sites. Неуказанный public allowlist допускает все корректные email; пустой или некорректный public allowlist закрывает путь с 503. Списки и секреты не включаются в конкурсный документ. Owner-only диагностика почты независима от регистрации и не включает её.

## 3. Локальная сборка и воспроизводимый запуск

Нужны доступ к приватному GitHub, Node.js 24.19.0, npm и доступ к npm registry. Команды выполняются в новом checkout из корня проекта. Не удаляйте использованное состояние другого разработчика.

```sh
git clone https://github.com/agent-axiom/axiom-lct-fsp.git
cd axiom-lct-fsp
npm run install:ci
npm run build
node scripts/migrate-local.mjs
node scripts/local-demo.mjs
```

Откройте `http://localhost:8888`. Прокси слушает loopback и добавляет вымышленную локальную identity; Worker работает на 127.0.0.1:8787. Прокси нельзя публиковать в интернет. Используйте только синтетические профили и адреса `@example.test`. Данные локальной D1 находятся в `.wrangler/state`, служебная конфигурация — в `.sites-runtime`.

Проверки запускаются отдельно от интерактивного сервера:

```sh
npm test
npm run typecheck
npm run lint
npm run build
node scripts/migrate-local.mjs
node scripts/verify-clean-launch.mjs
node scripts/verify-two-role.mjs
```

`verify-clean-launch.mjs` сам запускает и завершает локальный HTTP-сервер: проверяет главную без identity, отказ доступа к личному API и гостевой API. Перед запуском освободите порт 8787. `verify-two-role.mjs` проверяет синтетические роли и SQLite/HTTP-переходы; он не доказывает доставку писем или вход двух настоящих пользователей.

Альтернативный путь — `docker compose up --build`: порт опубликован только на 127.0.0.1:8888, состояние хранится в `demo-data`. Docker-конфигурация поставляется, отдельный успешный финальный Docker-прогон не подтверждён. Команда `npm run start` запускает Worker из production-артефакта; простой `dev` не заменяет проверку production-сборки и миграций.

Результаты старых прогонов не переносятся автоматически на новый email-код. Итоговый протокол должен содержать точный commit, версии Node/npm, команды, коды завершения и статус чистого запуска. Успешная установка не равна успешной сборке, а сборка не равна браузерной приёмке.

## 4. Публикация и две истории миграций

У канонического репозитория и исторического сайта Sites v12/v13 разные последовательности миграций. Приложение общее, но одинаковый номер SQL-файла может означать разные изменения базы. Нельзя применять mainline-цепочку поверх существующей Sites-базы или смешивать обе истории.

| Цель | Выбранная цепочка |
|---|---|
| Новая локальная база mainline | drizzle/: 0000–0007; новая 0007_public_email_auth.sql |
| Продолжение исторической Sites-базы | migration-profiles/sites-v12/: 0000–0006; новая 0006_public_email_auth.sql |

Mainline содержит `0004_email_payload_fingerprint`, `0005_email_transport`, `0006_mature_lady_mastermind`. Sites сохраняет свой исходный `0004_rainy_millenium_guard` и добавляет `0005_align_mainline_email_columns`. Обе новые auth-миграции добавляют запросы подтверждения, сессии и rate-limit таблицу; они не включают почту, не удаляют профили и не меняют runtime flags.

Подготовка stage выполняется из **чистого commit** с установленными зависимостями:

```sh
node scripts/verify-sites-v12-profile.mjs
node scripts/prepare-sites-v12.mjs \
  --output /absolute/empty/fsp-site-stage
```

Скрипт отказывается работать с грязными tracked-файлами, устаревшим schema/profile, неподходящим Site ID, symlink output и output внутри checkout. В отдельный stage копируются tracked-исходники и выбранная история; `SOURCE-PROVENANCE.json` сохраняет source commit и хеши файлов. Затем в stage устанавливаются lockfile-зависимости, выполняется сборка и проверка миграций на отдельной свежей локальной базе. Обычный полный regression suite остаётся в каноническом checkout: некоторые тесты намеренно проверяют mainline SQL.

Публикация — отдельная операция поддерживаемого Sites workflow. При интеграции сохраняются `.git` и `.openai/hosting.json` Site checkout. В итоговом manifest нужны app commit, Site source SHA, версия публикации, миграционный профиль и подтверждённый статус deployment. Site SHA может отличаться от GitHub SHA из-за выбранной истории и provenance; это должно быть объяснено, а не скрыто.

Возврат к старому Worker не удаляет уже добавленные таблицы/колонки. После неудачной публикации сначала проверяют фактическую схему и статус миграций. Ограниченный экспорт строк не считается полноценной резервной копией; подтверждённой production-процедуры восстановления в этом документе нет.

## 5. Архитектура, профиль и разграничение ролей

Общий путь: браузер React → route handler Worker → проверка identity/session и Origin → доменный сервис → D1 repository → безопасный DTO → интерфейс. Бизнес-правила доступны без UI; извлечение требований и начисление баллов проверяемы по отдельным компонентам.

| Слой | Основные исходники |
|---|---|
| UI / маршруты | app/workspace.tsx, app/account/portal.tsx, app/api/* |
| Домен | lib/domain.mjs: профиль, тест, поиск, приглашения, статусы |
| Подбор / доказательства | lib/matching.mjs, lib/achievements.mjs, lib/evidence.mjs |
| Тест | lib/assessment.mjs, lib/assessment-fresh.mjs |
| Реальные аккаунты | lib/public-email-auth.mjs, lib/public-account-http.mjs, lib/real-accounts.mjs |
| Гость / legacy | lib/guest-demo.mjs и отдельные trusted-principal handlers |
| Хранение / PDF | db/schema.ts, Drizzle migrations, lib/pdf.ts |

Гостевой режим хранит изолированное синтетическое пространство с cookie и сроком два часа. Он не читает реальные аккаунты. Переключатель ролей внутри такого пространства служит демонстрации; он не является авторизацией двух независимых пользователей. Публичный email-контур получает principal только из серверной сессии. Переданные клиентом actor, role или email не выбирают владельца команды и не меняют чужой профиль.

Кандидат вводит описание опыта, стаж и soft skills вручную. Самоописание не добавляет подтверждённые skills. При успешном тесте сервер записывает категорию, версию банка, результат и подтверждённые навыки по блокам. Старые результаты сохраняются в истории; при несовместимой версии требуется новый тест. Начальные демо-баллы отмечены как синтетические и не имеют выдуманной даты прохождения.

Собственный PDF генерируется `pdf-lib` со встроенным кириллическим шрифтом. Он содержит владельца, его контакт, учебную или демо-категорию, источник результата, при наличии — дату/версию теста, результаты навыков, описание, историю и DEMO-достижения. Endpoint PDF проверяет владельца и роль candidate. Наличие контакта в собственном файле не доказывает доступ работодателя к этому файлу.

Каталог требует подтверждённого email/допуска, опубликованного профиля, согласия и категории; для assessment evidence требуется согласованный текущий результат. Контакт работодателя доступен кандидату в предложении. Контакт кандидата возвращается пригласившему работодателю после принятия и пока действует согласие. Снятие публикации скрывает каталог, но само по себе не отзывает уже раскрытый контакт; отзыв согласия закрывает его в новых ответах сервера. Уже скопированную информацию автоматически отозвать нельзя.

## 6. Email-вход, данные и эксплуатационные ограничения

В `/account` обычный пользователь выбирает login либо register. При регистрации нужны email, имя/компания, роль и согласие с текущей версией политики. Один нормализованный email закрепляется за одной ролью. Пароль и ChatGPT для нового пути не требуются. Legacy Sites-principal аккаунты остаются отдельным контуром; автоматического объединения с ними нет.

`POST auth/request` сохраняет запрос и хеш браузерного nonce; **аккаунт ещё не создан**. Отправляется одна попытка письма через Resend. Ссылка содержит challenge и токен в URL fragment `/account/verify#…`, действует 15 минут и открывается в том же браузере. UI удаляет fragment из адресной строки и передаёт значения в JSON `POST auth/consume`. Правильный одноразовый токен и browser cookie атомарно создают/находят аккаунт и выдают сессию до 24 часов. В D1 хранятся хеши секретов; cookies — HttpOnly, Secure, SameSite=Lax. Logout отзывает текущую сессию.

POST проверяет Origin, JSON Content-Type и отвергает cross-site запрос. Неверные/просроченные/повторные ссылки и чужой браузер не дают сессию. Лимиты: одна ссылка в минуту и пять в час на email, 30 запросов в минуту на контур, до 128 активных запросов; неверных consume-попыток не больше пяти. Это ограничение нагрузки, а не полная защита от злоупотреблений.

Статус `accepted` означает приём запроса провайдером, не фактическое получение в inbox. Неопределённый сетевой исход хранится как `unknown`; новая ссылка — отдельный запрос после ограничения частоты. Owner diagnostic подтверждает только собственное диагностическое письмо, а не регистрационный путь кандидата и работодателя.

Сохраняются email, имя, роль, согласия, профиль, задания и результаты, история попыток, приглашения и последние 40 поисков работодателя. Исходный введённый текст ответов отдельно не сохраняется; черновик поддерживаемого режима находится в sessionStorage вкладки. Resend получает адрес и служебное письмо со ссылкой; профиль и тестовые результаты для этой отправки ему не передаются.

Реальные оператор/контакт, утверждённая политика и сроки хранения пока не получены. `/privacy` показывает эту незавершённость. API удаления аккаунта нет; отзыв согласия не удаляет историю. Очистка истёкших auth-записей выполняется при следующих запросах и не равна немедленному удалению. Регион хранения, отсутствие инфраструктурных журналов/копий и шифрование всех полей этим кодом не гарантируются. До операционной приёмки account flags остаются false, email — off.

## 7. Учебное тестирование v5 и процедура проверки

Кандидат выбирает Backend/Frontend и предполагаемый Junior/Middle/Senior. В попытке 12 заданий, 30 минут, четыре навыка по три задания. Для успеха нужны минимум 9/12 суммарно и 2/3 в каждом навыке; высокий общий балл не компенсирует провал одного блока. Каждый блок содержит свежую задачу с набором данных, прежнюю прикладную задачу и вопрос на знания. Банк — 168 семейств, включая 24 новых параметризованных семейства.

Backend проверяет Python, SQL, HTTP, Algorithms; Frontend — TypeScript, React, CSS, Accessibility. Сервер создаёт вариант, проверяет все ответы и сохраняет исходы задач. Public DTO не включает ключи ответов. Публичная квитанция показывает только согласованный результат, версию и итоги навыков. Провал не понижает грейд автоматически и не запускает cooldown; кандидат может повторить уровень. Успешная смена ранее подтверждённого грейда запускает ограничение 90 дней. Повышение версии банка требует повторной актуальной проверки, сохраняя историю.

Методика v5 использует авторские seeds, синтетические профили и эталон вычислений. После первого прогона изменён Frontend Junior и удалено неиспользуемое SQL-поле; итог снова измерен на тех же seeds. Это адаптивная разработка, не новый независимый holdout и не психометрическая валидация людей.

| Категория | Точное запоминание v4 → v5, 500 training форм / 300 вариантов | Modal fallback v5 |
|---|---|---:|
| Backend Junior | 89.00% → 0.00% | 35.67% |
| Backend Middle | 95.67% → 1.33% | 49.33% |
| Backend Senior | 90.00% → 0.00% | 22.67% |
| Frontend Junior | 89.00% → 0.00% | 12.33% |
| Frontend Middle | 89.00% → 0.00% | 21.67% |
| Frontend Senior | 90.00% → 1.00% | 29.33% |

Доли — успешные зачёты конкретной модели запоминания, не ошибка оценивания компетентности. Modal fallback угадывает наиболее частый ответ неизвестного семейства и был добавлен после основного протокола. Значит, снижение точного воспроизведения текста не решает общее заучивание/угадывание. Частичные фиксированные профили также меняют pass/fail между вариантами: разброс около 41–46% пар в сохранённой процедуре. Профессиональная валидность грейдов, сопоставимая сложность у людей и устойчивость к LLM/анализу исходника не доказаны.

Воспроизведение: `node scripts/evaluate-assessment-v5.mjs` и `node scripts/evaluate-assessment-modal.mjs`. Перед запуском проверить поддерживаемые аргументы скрипта: evaluator может обновлять сохранённый отчёт; для неизменяемой поставки нужен отдельный checkout. Контракт, seeds и подробные результаты — `docs/assessment-quality-v5.md` и `tests/fixtures/assessment-v5/`.

## 8. Объяснимый подбор и подтверждения ФСП

`parseRequirements` извлекает ограниченный словарь специализации, грейда, технологий и простого минимального стажа. Явные specialization, grade, skills и FSP-фильтры жёсткие и имеют приоритет над текстом. Свободный текст — мягкие признаки; сложные альтернативы и верхние границы стажа требуют ручной проверки. Поддержана локальная OR-пара навыков; отрицание «не требуется» снимает положительный вклад, но не запрещает кандидата со знанием технологии.

| Компонент распознанных требований | Относительный вес |
|---|---:|
| Специализация; грейд | 25; 20 |
| Подтверждённый стек / OR-группы | 45 |
| Минимальный опыт, самоописание | 10 |
| Непроверенные явно обязательные условия | 45, вклад 0; один компонент |

Активные веса нормируются: соответствие требованиям даёт 80% базового балла, результат учебного теста — 20%. Если требований не распознано, используется тестовый балл. DEMO-достижение даёт максимум +5 с ограничением итогом 100: только при точном совпадении текущей категории и всех требований, без unverified/missing. Достижения не повышают грейд, бонусы не суммируются без границы. Это инженерная формула, не вероятность успешного найма.

Явно обязательное неизвестное условие, например «обязателен Rust», сохраняется в unverifiedRequirements, missing и предупреждениях; полный match не заявляется, ФСП-бонус равен нулю. Защитный parser не понимает все формулировки, поэтому обычная карточка описывает балл «по распознанным условиям». «Нет данных» не означает «кандидат не умеет». Историческое DEMO-достижение после смены категории остаётся видимым и доступным FSP-фильтру, но не получает бонус в новой категории.

План реальной интеграции ФСП: отдельный адаптер, устойчивый ID участника, проверяемый способ привязки, источник/время проверки, idempotent импорт, сохранение истории и явное разделение индивидуального/командного результата и роли. Сегодня этот контракт не доказывает владение реальным ФСП ID: реальные аккаунты не получают синтетическую верификацию автоматически.

Исторический frozen benchmark: 36 профилей × 36 запросов, 1296 авторских labels, P@5 считает labels≥2, NDCG gain=2^label−1; один zero-IDCG исключается только из NDCG. На старом `fd457202` ретроспективное сравнение дало P@5 current/exact/alias = 0.8556/0.7111/0.7167 и NDCG = 0.9900/0.8037/0.8158. Current проигрывал P@5 на трёх запросах. Старый heldout просмотрен, рубрика благоприятствует rules; это не качество найма или значимый рыночный эффект. Новый matcher менялся после этой проверки: старые числа не выдаются за новый прогон. Все выдачи и ограничения сохранены в отдельном `fsp-review/keyword-comparison/`.

## 9. HTTP API и контракты

Полная спецификация — `docs/openapi.json`; актуальный handler остаётся источником фактического поведения. Секреты, токены, private runtime и персональные идентификаторы не включаются в примеры. Ответы личного кабинета и auth используют no-store; публичные auth endpoints зависят от HTTPS cookie текущего браузера.

| Метод и маршрут | Назначение / граница |
|---|---|
| GET /api/public-account/state | Состояние email-кабинета; при выключении — enabled=false |
| POST /api/public-account/auth/request | login/register; запрос письма и привязка к браузеру |
| POST /api/public-account/auth/consume | Одноразовый challengeId + token из fragment; создание сессии |
| POST /api/public-account/auth/logout | Отзыв текущей сессии и очистка cookies |
| POST /api/public-account/action | Команда закреплённой роли; actor берётся с сервера |
| GET /api/public-account/profile.pdf | Только собственный подтверждённый профиль кандидата |
| /api/guest/state, /candidates, /profile.pdf, /action | GET чтение, POST action; изолированное гостевое пространство |
| /api/state, /candidates, /profile.pdf, /action | Персональное демо по доверенной Sites identity |
| /api/account/state, /action, /profile.pdf | Отдельный legacy реальный контур Sites-principal |
| GET/POST /api/owner/email-test, /domain-email-test | Две owner-only диагностики; не регистрация |

В public account `/action` разрешены `profile`, `company`, `test-start`, `test-submit`, `search`, `invite`, `invitation-status`. `register`, `switch`, guest reset и синтетическая привязка `fsp` туда не допускаются. Публичное создание аккаунта выполняется только через auth request/consume.

Регистрация передаёт mode, email, name, role, dataConsent и текущую privacyNoticeVersion. Поиск — need и explicit filters. Приглашение — candidateId, description, целые salaryFrom/salaryTo в RUB, salaryBasis gross/net. Диапазон положительный, верхняя граница не меньше нижней. Статусы: sent → viewed → accepted/declined; повторное решение отклоняется. Принятие требует согласия кандидата; отправка требует доступного профиля и заполненной компании.

Основные ошибки: 400 — неверные поля/ссылка; 401 — нет сессии; 403 — чужая роль, Origin, allowlist или неразрешённое действие; 404 — неизвестный ресурс; 409 — повтор/конфликт состояния; 413 — лимит тела; 415 — не JSON; 429 — частота; 503 — выключенный/неполностью настроенный режим или недоступный сервис. В URL query не разрешаются token/session/principal/owner/account. Страница `/privacy` описывает фактическую обработку и незаполненные реквизиты; она не заменяет решение реального оператора о целях и сроках.

## 10. Демонстрация, доступ жюри и текущая приёмка

Питч по FAQ организаторов — 10 минут. Сначала показать, что данные synthetic; затем категорию и свидетельства кандидата, запрос работодателя с одним совпадением и одним пробелом, приглашение с зарплатой, принятие, открытие контакта только соответствующему работодателю, отзыв согласия и собственный PDF. Для полного сценария кандидат действительно отвечает на тест: seed-профиль допустим как отдельная демонстрация, но не как измеренный результат прохождения.

В новом email-контуре требуются два контролируемых inbox и две независимые браузерные сессии: registration → полученное письмо → same-browser consume → профиль/тест → поиск/приглашение → ответ/контакт. Проверить logout/login, refresh, expiry, replay, чужой браузер и отказ до подтверждения. Гостевой переключатель и mock email не заменяют эти шаги.

| Свидетельство на момент подготовки | Подтверждение / ограничение |
|---|---|
| База main 4910d03, PR #11 | Ранее подтверждённый CI; не новый рабочий email-код |
| Публичный email backend | 41 локальный тест с SQLite/mock; независимые probes также прошли |
| Privacy configuration | 3 локальные проверки; оператор и контакт ещё не заданы |
| Миграции auth | Native SQLite и согласованность двух chains проверены; финальный D1/profile/production проход требует релизного прогона |
| Финальная сборка/CI | Предварительный документ: итоговый успех всего рабочего набора пока не зафиксирован |
| Live email, два пользователя | Не подтверждены; acceptance/provider receipt не равен inbox delivery |
| Финальная публикация и браузер | Совпадение source SHA и новый полный E2E не подтверждены |
| Слайды, код для жюри, видео | Доступ и готовый комплект проверяются отдельно; сценарий не является записанным видео |

Итоговый релиз обновляет эту таблицу после фактических проверок с точным commit/CI URL, app/Site SHA и обезличенным browser protocol. Не переносить старые числа программных тестов на новый код. Нет подтверждённой production-нагрузки, полного мобильного прогона и профессиональной валидации теста.

По ТЗ финальная сдача включает ссылку на исходники, презентацию PPTX/PDF и документацию DOC/PDF. Работающий доступный стенд крайне желателен; при его отсутствии обязательны демонстрационное видео и инструкция локального запуска. При доступном стенде резервное видео полезно, но не отдельное обязательное требование. Приватный GitHub требует проверенного чтения/скачивания жюри. Слайды 7–11 шаблона, данные команды, канал сдачи и факт отправки подтверждаются отдельно; настоящий API ФСП для MVP не требуется.

Этот документ и его PDF созданы локально, ничего не отправляют организаторам и не свидетельствуют о финальной подаче. До включения реальной регистрации необходимо завершить операторские данные, политику/хранение и контролируемую live-приёмку.
