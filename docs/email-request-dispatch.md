# Отправка проверочного письма из аутентифицированного HTTP-запроса

Изолированное изменение поверх Site source `6eec31d631be9091843a28f12c16d6bfa9183fbd`, tree `a5f1eab7555860b090da0a83299a5e26047cc0be` (эквивалент GitHub main `e91a3554b5f1674e4269c7a5b19b5add83429044`). Реальные аккаунты и email остаются выключенными по умолчанию. Эти изменения не являются активацией или проверкой реальной доставки.

## Что изменилось

- RealAccountsService не вызывает транспорт. После его успешного register/email-request/email-retry HTTP handler ожидает максимум один POST к Resend для точного server-selected challenge.
- Principal берётся только из доверенного адаптера Sites. Проверка Origin выполняется до записи или отправки. Dispatch повторно связывает challenge с этим principal в SQL. email-request/email-retry не принимают accountId, recipient, email или challengeId.
- Повтор регистрации возвращает существующий аккаунт, его неизменные роль/email и новейший существующий challenge. Он не создаёт повторный challenge. После потерянного ответа повтор может безопасно завершить тот же job; действующий lease и backoff соблюдаются.
- email-retry повторяет новейший существующий запрос. Если его нет, ничего не создаётся. email-request отдельно создаёт новую ссылку под лимитами частоты и отправляет именно её, не старую очередь и не письма других аккаунтов.
- GET state никогда не отправляет почту. UI показывает статус, доступность и время явного повтора, предлагает обновить статус и запросить новое письмо. Фоновые автоматические повторы не обещаются и не запускаются.
- Миграция 0004 добавляет одну nullable колонку payload_hash в real_email_outbox. Сохраняется только SHA-256 exact JSON payload, без plaintext токена/письма/ключа. Профили, оценки, история и остальные таблицы не меняются.
- На повторе проверяются token hash и payload hash. Смена secret, sender, origin или шаблона останавливает попытку. API-key rotation не меняет письмо. Старый job без fingerprint может получить hash до первой попытки; ранее начатый legacy job без fingerprint завершается fail-closed и требует нового письма.
- Устаревший job, сменившийся email, использованный/истёкший challenge или пять неверных токенов не отправляются. Подтверждение аккаунта во время HTTP не реактивирует новую ссылку. Старый поздний ответ не отзывает новую принятую ссылку. Письмо, уже переданное провайдеру, невозможно отозвать при параллельном изменении аккаунта; проверка ссылки всё равно закрывается.

## Проверенные границы

- Максимум один provider POST на register/email-request/email-retry; никакого общего drain endpoint.
- Lease 60 с, timeout всей transport/json операции 10 с, включая mock, игнорирующий AbortSignal.
- Не больше пяти claims/попыток на challenge, включая падение после принятия провайдером и до фиксации результата. Отказы до транспорта могут использовать попытку, но не дают дополнительных отправок.
- Backoff после ошибок: 60, 120, 240, 300 секунд; пятая попытка терминальная. Истечение 15-минутной ссылки может остановить поздний повтор раньше лимита.
- Новые challenges не чаще одного в минуту и максимум пять за час; регистрация входит в этот лимит.
- Успех требует корректного 2xx и непустого строкового provider ID. Это принятие провайдером, а не доказательство получения письма.
- Предыдущий принятый токен остаётся действительным до принятия нового, собственного expiry, использования или блокировки пятью ошибками. Неуспешный resend сам по себе не отзывает предыдущую ссылку.
- Идемпотентность на внешней границе зависит от контракта Resend. Локальная очередь не доказывает exactly-once delivery.

## Локальные проверки

Синтетические адреса `example.test`, временная SQLite и mock HTTP; реальных писем и credentials нет.

```sh
node --test tests/email-dispatch-http.test.mjs
npm test
npm run typecheck
npm run lint
npm run build
```

Mock HTTP покрывает начальную отправку, OFF и переход OFF→live, trusted principal/origin/foreign target, потерю ответа до/после provider acceptance, replay без изменения аккаунта, конкуренцию, активный lease, backoff/пять попыток, permanent/transient/malformed 2xx, timeout, приоритет newest resend, действительность/отзыв токенов, late-response race, срок/использование/неверные токены, изменение/удаление и подтверждение аккаунта, race между чтением токена и commit проверки, изменение конфигурации и legacy jobs. Отдельный upgrade-тест сравнивает строки всех существующих таблиц до/после additive миграции. Существующие outbox, account и остальные регрессионные тесты сохранены.

## Результат проверки в изолированном executor

На 2026-10-08 полный набор из 229 tests, typecheck, lint и production build прошёл. Реальный transport timeout отдельно проверен mock-запросом, который игнорирует AbortSignal; HTTP завершился через 10 секунд.

Дополнительно подготовлен UI-only сценарий `tests/email-dispatch-browser.mjs`: desktop/mobile, backoff, повторный click, сетевое прерывание, отдельные retry/new-request, OFF и terminal status. Все account API в нём перехватываются; runtime остаётся OFF. Его запуск заблокирован самим executor до открытия страницы (Chromium socket permission, затем ошибка sandbox mount при проверенном повторе). Browser pass и screenshots не подтверждены. Перед активацией его нужно запустить в поддерживаемом браузерном окружении:

```sh
npm run dev -- --host 127.0.0.1 --port 5274
# В другом процессе:
FSP_TEST_URL=http://127.0.0.1:5274 CHROMIUM_PATH=/usr/bin/chromium node tests/email-dispatch-browser.mjs
```

## Что остаётся до активации

1. Утвердить privacy notice/version, оператора данных, сроки хранения и удаления.
2. Утвердить принадлежащий владельцу sender/domain и контролируемый тестовый inbox; разрешить передачу данных Resend.
3. Безопасно настроить отдельно разрешённые credentials и token secret, не через чат/Git. Проверка формы config не доказывает права на sender, действительность key или случайность secret.
4. Применить additive миграцию, проверить request-time runtime и реальные ограниченные browser/e2e-пути на двух аккаунтах, включая login interruption, logout, mobile, фактическое получение и анти-abuse.
5. Только затем отдельно включать режим. Cron/Sites background support не проверены; unattended retry остаётся отдельной будущей задачей.
