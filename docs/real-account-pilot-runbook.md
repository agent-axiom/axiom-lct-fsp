# Реальные аккаунты: закрытый пилот и границы доказательств

Этот документ описывает legacy-вход через доверенный Sites/ChatGPT principal. Для нового кабинета обычного email без ChatGPT используйте [public-email-account-runbook.md](public-email-account-runbook.md); в его пилоте legacy-список Sites IDs задаётся как `[]` и старый путь закрыт. Прежние утверждения о входе ChatGPT ниже относятся только к legacy-контуру.

Дата: 2026-10-10. Интеграционная база этой ветки: GitHub main `a712f828da7147925cd653d8e8c1ac498ff1940d`. Предварительная проверка patch выполнялась на основе `fd4572022c367645784232f517ae2f91a07e646b` и исторического исходника Sites v13 с 301/301 совпавшими SHA-256 из SOURCE-PROVENANCE.json. Это отдельные записи происхождения; номер текущей live-версии определяется последней успешной публикацией. Пилотные изменения пока не применялись к live, credentials не создавались и не менялись, настоящих писем эта проверка не отправляла.

## Что добавлено

- Необязательный серверный `FSP_REAL_ACCOUNT_PILOT_SUBJECTS`: JSON-массив 1–100 непустых строк до 256 символов без крайних пробелов. Хранить реальные ID только в защищённой runtime-конфигурации, не исходниках и не примерах.
- При заданном параметре допускаются исключительно доверенные principal с issuer `sites-chatgpt` и subject из списка. Некорректный JSON, пустая строка/список, нестроковые элементы закрывают доступ HTTP 503. Пользователь вне списка получает 403 до чтения/записи аккаунта или отправки.
- Проверяются и state, и actions, и PDF; JSON, cookie, query или произвольный client header не выбирают principal. Внешний доверенный Sites adapter остаётся необходимым.
- При отсутствующем параметре действует прежний режим для всех вошедших ChatGPT-пользователей. Поэтому не удалять allowlist при пилоте; его удаление является отдельным расширением запуска. Общий флаг аккаунтов по умолчанию false.
- Для неподтверждённого реального аккаунта ролевые действия теперь возвращают корректный 403 «Сначала подтвердите email», без ошибочного упоминания демо-адреса.
- Новый `tests/real-account-pilot.test.mjs` проверяет HTTP handler + SQLite + настоящий код outbox/transport с локальным injected fake fetcher. Provider URL только сравнивается в памяти; сетевых запросов нет.

## Что действительно доказано тестом

1. Регистрация разных candidate/employer principal создаёт разные аккаунты с закреплённой ролью и отправляет по одному payload в fake transport.
2. Ссылка берётся из текста captured письма, а не вычисляется тестом из секрета. Origin корректен, токен находится во fragment, а не query; чужой аккаунт и повторное применение ссылки отклоняются.
3. До подтверждения email нельзя начать тест/поиск; имя роли, actor ID и контакт из JSON не дают дополнительные права.
4. Ручная анкета/публикация не дают категорию; выбор Backend/Junior, 12 вопросов, возобновление теста через свежий state, сдача и запись категории/истории работают. Эталонные ответы берутся только из приватной fixture DB, не из публичного API.
5. Работодатель ищет подтверждённого кандидата, отправляет приглашение с диапазоном RUB и net; viewed не открывает контакт. Принятие без consent запрещено; принятие с consent раскрывает только подтверждённый email пригласившему работодателю. Третий проверенный работодатель не получает контакт или чужие приглашения.
6. Повторное терминальное решение запрещено; отзыв согласия скрывает профиль из поиска и контакт из уже принятого приглашения. Повторные GET, тест, профиль и hiring-действия не отправляют почту.

Это программная интеграционная проверка. Она не доказывает получение настоящего письма, независимые браузерные сессии, защиту заголовков на edge, антиспам при публичной регистрации, юридическое соответствие или экспертную валидность тестового банка.

## Runtime-конфигурация закрытого пилота

Значения ниже — план, не выполненное изменение:

| Переменная | Требование |
|---|---|
| FSP_REAL_ACCOUNTS_ENABLED | `true` только после разрешения на ограниченный пилот |
| FSP_REAL_ACCOUNT_PILOT_SUBJECTS | JSON-массив **двух заранее проверенных Sites user IDs**, кандидат и работодатель; одного ChatGPT ID недостаточно для двух ролей |
| FSP_EMAIL_MODE | `live` только после разрешения на реальные проверочные письма |
| FSP_EMAIL_TRANSPORT | `resend` |
| FSP_EMAIL_FROM | `noreply@notify.kosarevsky.dev`, после отдельного успешного доменного diagnostic |
| FSP_SITE_ORIGIN | `https://axiom-fsp-talent.major-tick-1728.chatgpt.site` пока custom domain не работает |
| FSP_PRIVACY_NOTICE_URL | Доступный HTTPS URL утверждённой политики реальных данных |
| FSP_PRIVACY_NOTICE_VERSION | Утверждённая непустая версия, с которой согласится каждый участник |
| RESEND_API_KEY | Уже разрешённый действующий secret с правом отправки с выбранного домена; не читать/печатать и не создавать в этом шаге |
| FSP_EMAIL_TOKEN_SECRET | Отдельно безопасно установленный secret длиной не менее 32 символов; проверка длины не доказывает энтропию |

`notify.kosarevsky.dev` verified и `fsp.kosarevsky.dev` pending — сведения от владельца задачи; в этой проверке DNS/провайдер повторно не запрашивались. Пока отсутствуют DNS custom domain, запрещено ставить его в site origin: ссылки уйдут на неработающий адрес. Не менять origin/sender/шаблон/token secret при действующих jobs: payload pinning закроет повтор (`PAYLOAD_CHANGED` / `TOKEN_KEY_CHANGED`), потребуется новый запрос.

`FSP_OWNER_EMAIL_TEST_ENABLED` и `FSP_OWNER_EMAIL_TEST_TO` относятся к отдельному owner-only diagnostic и не включают регистрацию. Диагностическое письмо не подтверждает email аккаунта. Реальные Google relay переменные этому пилоту не нужны.

## Точный порядок запуска после согласований

1. Слить/опубликовать изменения с runtime `accounts=false`, `email=off`. Для существующей базы с историей Sites v12/v13 сохранить **sites-v12 migration profile**, не проигрывать mainline 0004–0006 поверх неё. Новым изменениям миграция не нужна. Повторить typecheck/lint/build, regression и provenance на финальном объединённом коде.
2. Отдельно завершить owner-only доменное письмо с фиксированным sender и разрешённым inbox; получить подтверждение фактического получения, проверить From, spam и рабочие SPF/DKIM/DMARC по доставленному сообщению. Это отдельная работа, не продублированная здесь.
3. Оператор утверждает политику, перечень данных, хранение/удаление, права доступа и условия передачи email провайдеру; оба участника соглашаются на пилот и использование конкретных адресов. Согласовать две независимые ChatGPT-сессии и серверно проверенные Sites user IDs.
4. Через разрешённую secure runtime-процедуру проверить наличие настроек и secrets без раскрытия значений. Новое/расширенное постоянное право доступа или ввод credentials выполняется только через требуемое отдельное подтверждение/защищённый handoff.
5. **До** общего флага установить валидный allowlist двух IDs. Подготовить origin/privacy/sender/transport. После отдельного разрешения переключить email в live и аккаунты в true. Проверить: неавторизованный API 401, неучастник 403; GET не отправляет писем. Не делать промежуточного запуска без списка.
6. В двух независимых браузерных профилях candidate/employer выполнить регистрацию, фактически получить письмо и подтвердить его под тем же ChatGPT входом. Проверить прерывание входа: исходную ссылку из письма открыть повторно после sign-in, так как секрет намеренно не сохраняется. Проверить неверный/просроченный/чужой/повторный токен и явный resend без массовой рассылки.
7. Кандидат: анкета и consent/publish → специализация/грейд → тест → категория и PDF своего профиля. Работодатель: компания → поиск → приглашение со ставкой. Кандидат: viewed → accepted. Работодатель видит контакт. Проверка независимого непригласившего работодателя остаётся синтетической в пилоте двух участников; live-проверка этой границы требует третьего отдельно согласованного участника и расширения allowlist. Отозвать consent и проверить сокрытие контакта после reload.
8. Сохранить обезличенный протокол с временем, версией приложения, статусами и фактом получения, не включая токены/ID/адреса в общий репозиторий. При сбое вернуть accounts=false и email=off; это блокирует доступ/новые отправки, но **не удаляет** уже сохранённые данные и не отзывает уже отправленные письма.
9. Публичный запуск — отдельное решение после retention/deletion процедуры, anti-abuse, нагрузки и проверки внешнего auth boundary. Удалять pilot allowlist без такого решения нельзя.

## Авторизация и ограничения

- `/api/account/*` получает principal только из `getChatGPTUser`: заголовки `oai-authenticated-user-id` и `oai-authenticated-user-email` должны поступать от доверенного Sites edge. Email header нужен adapter для входа, но контакт аккаунта — введённый и отдельно подтверждённый email. `oai-authenticated-user-full-name` необязателен. Вне Sites прокси обязан вычищать пользовательские заголовки и проверять реальную сессию; локальный demo proxy нельзя публиковать.
- POST обязан иметь Origin, совпадающий с origin URL запроса; UI отправляет `Content-Type: application/json`, но handler сам не валидирует Content-Type и разбирает JSON body. Размер JSON ограничен 16000 байт. Same-origin не заменяет проверку доверенного principal.
- Один trusted principal = одна роль и один email, смена роли повторной регистрацией запрещена. UI не реализует email/password вход; ChatGPT sign-in обязателен.
- Ссылка действует 15 минут, однократная, связана с аккаунтом; пять неправильных попыток закрывают её. Новое письмо: не чаще 1/мин и 5/час на аккаунт. Это не глобальный anti-abuse лимит.
- Dispatch выполняется только при register/email-request/email-retry. GET не посылает письма; cron и глобальный публичный drain отсутствуют. Transport timeout 10 с, lease 60 с, максимум 5 claims, backoff 1/2/4/5 мин. Provider acceptance не означает delivery.
- Есть только ручной профиль и минимальный выбор ИТ/Backend/Frontend/грейда; многошаговой отраслевой анкеты нет. ФСП API и подтверждение внешних достижений в real-режиме не подключены.
- Не закрыты этим patch: юридические/retention условия, ограничение регистрации emailMode=off (такой режим всё ещё может создавать неподтверждённые аккаунты), recovery/смена email/удаление аккаунта, нагрузка, публичный abuse-control, реальный браузерный mail flow.

## Обязательные оставшиеся подтверждения

- Разрешение на ограниченный live-пилот: два конкретных участника/ID, адреса, sender, Resend как получатель email для отправки проверочных писем, утверждённая политика/version, сроки хранения и назначение.
- Подтверждение безопасной настройки отсутствующих secrets или новых provider permissions, если обнаружатся; эта работа их не создавала.
- Фактическое получение доменного owner-test и затем двух настоящих регистрационных писем.
- Разрешение на более широкий публичный запуск отдельно от пилота.
