# Реальные аккаунты и transactional outbox — версия 0.4

## Граница готовности

Публичный Site остаётся синтетической демонстрацией. Новые UI/API и нормализованное хранение реализованы, но FSP_REAL_ACCOUNTS_ENABLED=false и FSP_EMAIL_MODE=off по умолчанию. Публикация кода не меняет эти настройки. Персональные данные новых реальных аккаунтов не собираются, внешние письма не отправляются. На /account показывается честный статус подготовки.

Рабочие модули: real-accounts.mjs (роли/сценарии), accounts-repository.mjs (D1/SQLite), email-outbox.mjs (очередь), real-account-http.mjs (HTTP), app/account (UI). account-service.mjs — прежняя чистая reference-модель, не runtime-реализация.

## Данные и границы доступа

10 новых таблиц из drizzle/0001_daffy_darkhawk.sql: real_accounts; real_candidate_profiles; real_employer_profiles; real_assessments; real_skill_evidence; real_invitations; real_searches; real_email_challenges; real_email_outbox; real_revisions. Демонстрационные workspaces не смешиваются с ними.

Unique(issuer,subject) и unique(email) обеспечиваются базой. Роль хранится в аккаунте и не меняется повторной регистрацией. Сервер получает principal только из доверенного Sites/ChatGPT-адаптера; присланные cookie, actor ID, email или role не создают аутентификацию. Email header ChatGPT сам по себе не считается подтверждением произвольного контактного адреса. Для работы нужен отдельный одноразовый email challenge.

Scoped SQL выбирает собственные записи, опубликованных согласившихся кандидатов для работодателя и стороны собственных приглашений. Контакт выдаётся только после принятия конкретному работодателю, при действующем согласии. Смена опубликованности/согласия учитывается при каждом чтении. Поиск и история ограничены владельцем.

Каждая бизнес-запись выполняется batch-транзакцией с CAS по real_revisions и уникальным operation ID. При конфликте все условные изменения пропускаются, клиент получает409. Это обеспечивает атомарность небольшого MVP, но глобальный revision сериализует записи. Высокая нагрузка и производительность на больших выборках не доказаны; перед масштабированием нужны более гранулярные транзакции и нагрузочные измерения.

## Почта без секретов в базе

Отдельный FSP_EMAIL_TOKEN_SECRET (не API key провайдера) используется для HMAC-SHA256 от immutable challenge: id, account_id, recipient, expires_at. Worker воспроизводит тот же токен для повтора. В challenge хранится SHA-256 токена; в outbox только challenge_id, status, lease, диагностический код и SHA-256 точного payload. Миграция 0004 добавляет nullable payload_hash и не меняет профили, тесты или историю. Секрет, API key, открытый токен и текст письма не сохраняются в таблицах очереди и не логируются.

Регистрация + профиль роли + challenge + outbox фиксируются одной транзакцией. Если вставка outbox падает, весь аккаунт откатывается. Ссылка действует15минут, одноразовая, только для конкретного аккаунта и адреса. Не более5 неправильных предъявлений; запрос письма не чаще1раза/минуту и не более5/час. Ошибочные попытки сохраняются при отказе. Проверка и email_verified_at изменяются транзакционно.

Ссылка несёт токен во fragment, а не query. UI удаляет fragment из текущей истории и требует подтверждения пользователем. При отсутствии входа нужно войти в исходный ChatGPT-аккаунт и повторно открыть письмо; сквозная проверка этого браузерного пути пока не выполнена.

## Отправка из HTTP-запроса и явный повтор

После авторизации и проверки Origin HTTP handler вызывает отправку только для собственного server-selected challenge: register создаёт его один раз; повтор register переиспользует новейший существующий запрос, не меняя роль/email; email-request создаёт новый challenge; email-retry переиспользует новейший существующий, ничего не создавая. Произвольные accountId/recipient/challengeId не выбирают цель доставки. RealAccountsService остаётся без транспорта. Один HTTP-запрос выполняет максимум один provider POST. GET состояния никогда не отправляет почту.

Порядок: атомарная запись очереди → claim по lease → HTTP Resend → атомарная фиксация результата. Lease60с, timeout транспорта10с, максимум5 попыток, backoff1–5минут; истёкшие/использованные challenges отменяются. Стабильный Resend Idempotency-Key относится к challenge; повтор после сбоя использует тот же payload и ключ. При смене sender, origin, шаблона или token secret попытка завершается fail-closed. Legacy-задание без hash можно инициализировать только до первой попытки; если попытка уже была, необходим новый challenge. Истёкший lease после пятой попытки не даёт шестой отправки. Это не самостоятельная гарантия exactly-once: исключение дублей на границе HTTP опирается на контракт idempotency провайдера.

Проверены два конкурирующих worker, transient/permanent failures, падение после успешного HTTP и до записи результата, истечение lease, смена token secret, неверный/истёкший токен и атомарный rollback. Все внешние ответы в тестах — mock. Настоящий транспорт не вызывался.

`drainEmailOutbox` остаётся отдельной не подключённой серверной функцией для будущего разрешённого планировщика; расписание/cron/публичный или общий drain endpoint не создавались. Поддержка Sites cron не подтверждена. Автоматических фоновых повторов нет: UI честно предлагает «Повторить ту же попытку», время backoff/lease и отдельный запрос нового письма. Предыдущая принятая ссылка остаётся действительной до принятия новой или собственного истечения срока. Неподтверждённый HTTP-ответ провайдера не отзывает старую ссылку. При emailMode=off он не берёт lease и не вызывает транспорт. Старые blocked-задания не отправляются автоматически после включения; нужно запросить новое подтверждение. Смена token secret делает старые задания неверифицируемыми и приводит к fail-closed, а не отправке неверной ссылки.

## Минимальное подключение после разрешения

1. Оставить существующий вход ChatGPT; новый IdP для этого варианта не нужен.
2. Утвердить оператора данных, privacy notice/version, хранение/удаление и допустимость реальных данных. Приложение требует актуальное согласие при регистрации; соответствие152-ФЗ не заявляется.
3. Выбрать принадлежащий владельцу домен или поддомен отправки и разрешить его DNS-верификацию в Resend.
4. Отдельно разрешить создание send-only ключа Resend, ограниченного этим доменом, и безопасную конфигурацию серверных secrets. FSP_EMAIL_TOKEN_SECRET — отдельный случайный секрет минимум32байта. Не передавать ключи в чате или Git.
5. Разрешить передачу Resend email регистрации и текста проверочного письма для доставки. Согласовать sender и один контролируемый тестовый адрес. Тарифы/расходы не выбирались.
6. Применить additive миграцию 0004 и проверить поддерживаемый request-time путь, общие anti-abuse лимиты/IP-защиту, наблюдаемость доставки и удаление истёкших challenge/outbox согласно утверждённому сроку хранения. Фоновый worker не требуется для выбранного явного пути; unattended повторы остаются отдельной будущей задачей.
7. Проверить два независимых аккаунта в браузере, получение настоящего письма, CSRF/IDOR, прерванный вход, resend/replay, logout и mobile. Только потом включать реальный режим.

Runtime-настройки перечислены в .env.example. Пустые значения не являются рабочей конфигурацией. Код не включает ничего автоматически и не создаёт учётные данные.
