# Проверка готовности почты перед подключением

Изменения подготовлены локально на основе `a39996c` (v0.6.1). Реальные аккаунты и внешняя почта остаются выключенными. Здесь нет рабочего подключения провайдера, подтверждения доставки или разрешения на обработку персональных данных.

## Исправлено

1. `assertEmailDeliveryConfiguration` используется при регистрации нового аккаунта, создании email challenge и запуске outbox worker. В режиме `live` неполные параметры, короткий/пустой секрет и некорректный HTTPS origin дают стабильный HTTP 503 до записи аккаунта/challenge/outbox или взятия lease. Прежний OFF-режим сохранён. Сбой настройки почты не закрывает доступ к уже подтверждённым аккаунтам.
2. Успешный HTTP-код провайдера считается принятием письма только вместе с непустым строковым ID в JSON. Пустой, некорректный или неполный ответ получает `INVALID_PROVIDER_RESPONSE`, обычный backoff и прежний лимит пяти попыток. Повтор использует тот же payload и Idempotency-Key. Письмо не отмечается отправленным и email не подтверждается из-за некорректного ответа.

Проверка конфигурации подтверждает только её структуру: она не доказывает действительность API key, права на домен, случайность секрета или готовность политики данных. Они проверяются отдельно после разрешения владельца.

## Регрессионные проверки

Все проверки используют синтетические адреса, SQLite в памяти и mock транспорта. Настоящие письма не отправляются.

```sh
node --test tests/outbox.test.mjs tests/real-accounts.test.mjs tests/real-http.test.mjs
node --test tests/*.test.mjs
npm run lint
npm run typecheck
npm run build
```

Новые случаи: отсутствующие параметры; пустой/короткий секрет; HTTP, путь, query, fragment или credentials в origin; отсутствие записей при отказе регистрации/resend; отсутствие lease/HTTP при отказе dispatch; некорректный JSON и отсутствующий/пустой/нестроковый provider ID; идентичность повторного payload/key; исчерпание пяти попыток; OFF-режим; сохранение blocked-заданий; доступ уже подтверждённого аккаунта при недоступной настройке почты.

## Текущий способ запуска после отдельного разрешения

HTTP-путь register/email-request/email-retry теперь ожидает не более одной отправки собственного server-selected challenge. Отдельный scheduler не нужен для этого ограниченного пути. `drainEmailOutbox` остаётся не подключённым; фоновых повторов, global/public drain endpoint, нового cron или credentials нет. Поддержка Sites cron не установлена и не предполагается.

Повтор после network ambiguity, malformed 2xx или потери ответа запускается явно через email-retry либо безопасный replay регистрации. Сохраняются тот же challenge, точный payload и Idempotency-Key; применяются lease 60 с, timeout транспорта 10 с, backoff 1/2/4/5 мин и максимум 5 попыток, в том числе после падения worker. Новое email-request создаёт другую ссылку под существующими лимитами 1/мин и 5/час. Предыдущая принятая ссылка отзывается только после принятия новой.

Миграция 0004 добавляет nullable SHA-256 payload_hash только в real_email_outbox. Никакие сырые токены, payload или credentials не сохраняются. Смена sender/origin/шаблона приводит к fail-closed; legacy-задания после попытки без fingerprint не повторяются. Полный перечень проверок и границ: `docs/email-request-dispatch.md`.

Первый тест реальной отправки выполняется только после утверждения домена, sender, политики, безопасной настройки credentials и конкретного контролируемого адреса. До этого режим `live` не включать.

Дополнительные условия общего запуска остаются в `docs/account-email-plan.md`: anti-abuse, сроки хранения и удаление записей, проверка двух независимых браузерных аккаунтов, вход после прерывания, resend/replay/expiry и фактическое получение письма.
