# Личный кабинет по email

Состояние на 11 октября 2026: на опубликованном сайте включён закрытый пилот для двух согласованных адресов; оператор и контакт получены. Два письма со ссылкой приняты Resend, но отклонены серверами получателей с причиной `Blocked due to content`. Получение письма и полный браузерный путь двух реальных участников **не подтверждены**. Исправление в этих исходниках отправляет короткий код без ссылок; локальные проверки используют синтетические адреса и mock Resend. Публикацию исправления и фактическую доставку проверяют отдельно.

Обычный пользователь регистрируется или входит по одноразовому восьмизначному коду из письма. Пароль и аккаунт ChatGPT не нужны. Канонический адрес кабинета — `https://fsp.kosarevsky.dev/account`; готовность DNS/TLS и доступность этого адреса проверяются перед включением. Гостевое демо остаётся отдельным пространством на синтетических данных.

## Как устроен вход

1. На `/account` пользователь выбирает вход либо регистрацию. Для регистрации нужны email, роль, имя/компания и согласие с текущей версией политики. Email нормализуется в нижний регистр. Один email соответствует одной закреплённой роли.
2. `POST /api/public-account/auth/request` создаёт только запрос и привязку к браузеру. Ответ содержит несекретный `challengeId`; сам код в ответе отсутствует и в D1 хранится только SHA-256. **Аккаунта ещё нет.** Одна попытка отправки выполняется через Resend; ответ `requested=true` не доказывает принятие провайдером или доставку. Автоматический повтор/cron не подключён.
3. Новое письмо содержит только короткий текст и восьмизначный код, без URL. Тема — «Код подтверждения ФСП». Пользователь вводит код в форму `/account` в том же браузере и профиле, где запросил письмо, затем нажимает «Подтвердить код».
4. Код и `challengeId` формы держатся только в памяти страницы. После refresh нужно запросить новый код; серверный минутный лимит сохраняется. Старые письма со ссылкой `/account/verify#challenge=…&token=…` принимаются до их исходного срока: fragment удаляется из адресной строки, а вход требует отдельного нажатия. GET страницы или API не подтверждает вход.
5. `POST /api/public-account/auth/consume` атомарно создаёт первый аккаунт, ролевой профиль и сессию либо входит в существующий email-аккаунт. Код действует 15 минут, используется один раз и блокируется после пяти неправильных попыток. Принимается только строка из восьми ASCII-цифр; `code` и legacy `token` одновременно отклоняются. Генератор использует криптографический источник с rejection sampling, сохраняя ведущие нули и равную вероятность всех кодов. Повторная регистрация не меняет роль/имя; существующий Sites-аккаунт с тем же email автоматически не объединяется.
6. Серверная сессия действует 24 часа. Logout отзывает именно текущую сессию и очищает cookies. Другие выданные сессии и сохранённые данные не удаляются.

Сервер получает principal из случайного `__Host-fsp_account`, сверяя SHA-256 с D1. Cookie имеет `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, без Domain. `__Host-fsp_auth` отдельно связывает proof с браузером. JSON, query, заголовки, `actor`, `role`, `email` и `contact` не выбирают чужой аккаунт. В контактах используется подтверждённый email.

## API

Полный контракт: [openapi.json](openapi.json). Все ответы имеют `Cache-Control: no-store`; POST требует Origin текущего сервиса и `application/json`, размер body не больше 16000 байт. `Sec-Fetch-Site: cross-site` отклоняется. GET auth/action возвращает 404. Код, токен и session нельзя передавать в query.

| Метод и путь | Поведение |
|---|---|
| `GET /api/public-account/state` | Анонимный/выключенный статус либо собственный кабинет; без session возвращает `enrolled=false`, `user=null` |
| `POST /api/public-account/auth/request` | `{mode:"login",email}` либо регистрационные `mode,email,role,name,dataConsent,privacyNoticeVersion`; только запрос письма, ответ `requested,challengeId,message`, без кода |
| `POST /api/public-account/auth/consume` | `{challengeId,code}` и исходный browser cookie; legacy `{challengeId,token}` для уже отправленных ссылок; одна атомарная операция |
| `POST /api/public-account/auth/logout` | Пустой JSON; отзывает текущую session, очищает оба cookie, писем не отправляет |
| `POST /api/public-account/action` | Только `profile`, `company`, `test-start`, `test-submit`, `search`, `invite`, `invitation-status`; доступ по закреплённой роли |
| `GET /api/public-account/profile.pdf` | PDF собственного подтверждённого кандидата; работодатель и чужие идентификаторы не получают чужой PDF |

Лимиты запросов: один в минуту и пять в час на email, 30 в минуту глобально, менее 128 активных неподтверждённых запросов. Это ограничение частоты запросов, не гарантия доставки пяти писем. Превышение даёт 429. Истечение/неверный код или ссылка — 400, конкурентный конфликт — 409, отсутствие session для действия/PDF — 401, роль/Origin/закрытый pilot — 403, неполная конфигурация — 503. Запрос нового кода выполняется явно через форму; истёкшее подтверждение не восстанавливается.

## Настройки до включения

Публикация кода не меняет runtime-флаги. Для нового окружения до готовности оператора и двух inbox оставьте `FSP_REAL_ACCOUNTS_ENABLED=false`, `FSP_EMAIL_AUTH_ENABLED=false`, `FSP_EMAIL_MODE=off`.

| Настройка | Значение для ограниченного email-пилота |
|---|---|
| `FSP_SITE_ORIGIN` | `https://fsp.kosarevsky.dev`, после проверки DNS/TLS; форма на другом домене перенаправляет сюда |
| `FSP_REAL_ACCOUNT_PILOT_SUBJECTS` | `[]`: закрывает отдельный legacy `/api/account/*`, связанный с ChatGPT |
| `FSP_PUBLIC_ACCOUNT_PILOT_EMAILS` | JSON-массив двух согласованных inbox; реальные значения передаются в runtime, не коммитятся |
| `FSP_PRIVACY_NOTICE_URL` / `FSP_PRIVACY_NOTICE_VERSION` | Утверждённая оператором доступная HTTPS-политика и её непустая версия |
| `FSP_EMAIL_TRANSPORT` | `resend`; новый email-only путь не использует Google MailApp |
| `FSP_EMAIL_FROM` | Согласованный sender на проверенном домене; право отправки и фактическое получение проверяются отдельно |
| `RESEND_API_KEY` / `FSP_EMAIL_TOKEN_SECRET` | Через защищённый runtime-workflow; не читать, не печатать, не хранить в Git. Для совместимой конфигурации token secret не короче 32 символов |
| `FSP_EMAIL_MODE` | `live` только после подготовки ограниченного пилота |
| `FSP_REAL_ACCOUNTS_ENABLED` / `FSP_EMAIL_AUTH_ENABLED` | Обе `true` только после установки всех guard-параметров |

Неуказанный public allowlist разрешает все корректные email, поэтому для пилота его **нужно задать до включения**. Пустой или некорректный public allowlist даёт 503; адрес вне списка — 403. Список `[]` для legacy Sites — намеренное закрытие старого пути, а не public email allowlist. Owner-only diagnostic остаётся отдельным механизмом и не включает регистрацию.

## Порядок приёмки

1. Зафиксировать проверяемый commit; выполнить программные проверки и сборку на нём. Новая база использует mainline `0007_public_email_auth.sql`; существующая база Sites v12/v13 — [профиль sites-v12](../migration-profiles/sites-v12/README.md) с его `0006_public_email_auth.sql`. Не проигрывать две истории поверх одной базы.
2. Подтвердить оператора, политику, цели, сроки хранения/удаление и два inbox участников. Адреса и согласия не включать в общий отчёт. Настроить sender и secrets защищённым способом.
3. Проверить канонический домен и почту владельца отдельным diagnostic. Получение этого письма не доказывает регистрацию кандидата/работодателя.
4. Задать оба allowlist и policy до флагов. После подготовленного включения проверить anonymous state, запрет чужого адреса и закрытие legacy. Не делать промежуточного запуска с пустым guard.
5. В двух независимых браузерных профилях выполнить регистрацию кандидата и работодателя. Зафиксировать фактическое получение обоих писем и same-browser подтверждение кода без ChatGPT. Проверить logout/login, неправильный браузер, refresh с новым запросом, expiry, replay, неверный код и отказ до получения письма. Старую ссылку проверять только на синтетической legacy-фикстуре.
6. Кандидат: профиль/публикация/согласие → тест → категория → PDF. Работодатель: компания → поиск и объяснение → приглашение с RUB. Кандидат: принятие/отказ. Работодатель: контакт только после принятия; после отзыва согласия контакт исчезает при reload. Чужой работодатель проверяется синтетически; live-проверка требует третьего отдельно согласованного inbox.
7. Записать обезличенный протокол: commit, версия Sites, время, шаги, HTTP/браузерный результат и факт доставки. Не сохранять proof, session cookies, provider payloads или credentials. При сбое вернуть оба account-флага в `false`, email в `off`; это не удаляет данные и не отзывает отправленные письма.

## Подтверждённые проверки и пределы

На исходнике изменения кода прошли 43 локальных `public-email-auth` теста: существующие границы expiry/CSRF/конкурентной регистрации/consume, отсутствие URL в фактическом payload нового письма, отсутствие кода в JSON/базе, неверные и неоднозначные proof-поля, совместимость старого 64-hex proof. Они используют SQLite/D1 adapter и mock provider, настоящих писем не отправляют. Более широкий backend-набор проверяется отдельно; полный release-suite, production build, миграции на настоящем D1 и браузерная приёмка должны быть повторены на финальном commit. Не считать локальный pass доказательством активации.

В этой работе не подтверждены production-нагрузка, доставка, юридическое соответствие, восстановление/смена email, удаление аккаунта, нагрузочное anti-abuse и широкая публичная эксплуатация. Регистрация по email не доказывает профессиональную валидность учебного грейда. [Приоритеты и критерии приёмки](release-acceptance-checklist.md) разделяют обязательный минимум ТЗ и последующие улучшения.
